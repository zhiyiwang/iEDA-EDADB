# 原始iEDA、未优化EDADB与已优化EDADB：性能对比

只讨论milestone包含的P1/P3/P4/P5，不包含P2或后续profiling。版本、实现和计时说明分别见[demo.md](demo.md)、[transaction-batching.md](transaction-batching.md)、[stage-timing.md](stage-timing.md)。

## 1. 比较对象和方法

| 比较对象 | 实现与版本 |
| --- | --- |
| 原始iEDA | 接入EDADB前的 `007435241`，DEF文本读取/写出 |
| iEDA+EDADB未优化 | `62504bd9d / be6bbdd`，未加父键索引，建表及各root写入分别提交 |
| iEDA+EDADB已优化 | P1父键索引、P3/P4事务合并、P5流式Shadow；交付代码基于 `0da489453 / 494ce79`，iEDA标签本次仅增加四份文档更新，配对说明见[demo.md](demo.md) |

### 使用什么数据？

- 第2、3节及第7节主表都使用**同一份Sky130 GCD filler设计**：仓库内 `scripts/design/sky130_gcd/result/iPL_filler_result.def`，**726,155 B**。不是单表合成数据，也不是后文的routed压力数据。
- 该DEF声明2,604个Component、56个Pin、677个Net、2个SpecialNet、4个Via。三个来源的输入记录具有相同DEF SHA256，确认不是只用了同名文件。
- 原始iEDA读DEF文本并恢复iDB，写入从iDB输出DEF；EDADB读该设计生成的SQLite数据库并恢复iDB，写入从同一设计的iDB生成数据库。**比较同一个设计的两种存取实现，不是让两者读取同一种文件。**
- Release、热缓存，5次正式测量中位数，时间单位ms。Tcl在读写命令前后计时；LEF加载、写前输入准备及读后校验在计时外。

### 表中的时间从哪里取？

| 比较对象 | 原始统计文件（相对仓库） | 取用的行 |
| --- | --- | --- |
| 原始iEDA | `scripts/edadb/performance/native-baseline/summary.tsv` | `original`的`native_def_read/write`，取`median_ms` |
| 未优化EDADB | `scripts/edadb/performance/baseline-verification/summary.tsv` | `baseline/warm`的`edadb_read/write`，取`median_ms` |
| 已优化EDADB | `src/database/edadb/test/stream_shadow/results/summary.tsv` | `filler/stream/read或write/command_ms`，取`median` |

**三者采用已有不同批次结果：原始和未优化采用阶段计时OFF，已优化采用P5验收的ON。下面时间比和整体加速比是已有记录的概览，不是同批重新测出的严格净收益。** 已优化的测量core为 `1c4857c`；交付core之后合入默认关闭的SQL trace，未在最终标签重跑全矩阵。

**三者对比表采用“耗时倍数 = 各版本耗时 ÷ 原始iEDA耗时”**：原始iEDA为1，大于1表示耗时更多，越小越好。这不是加速比。读以47.484 ms为除数，写以6.855 ms为除数，不能混用。

优化前后仍用**“加速比 = 优化前耗时 ÷ 优化后耗时”**，大于1表示加速；耗时降低比例为 `1 − 优化后/优化前`。例如读取已优化/原始为135.813÷47.484=2.86倍耗时；未优化/已优化为11931.378÷135.813=87.85倍加速。

## 2. 整体读取：三者对比

| 实现 | 完整读取（ms） | 耗时倍数（该行÷原始iEDA） |
| --- | ---: | ---: |
| 原始iEDA | 47.484 | 1.00× |
| iEDA+EDADB未优化 | 11931.378 | 251.27× |
| iEDA+EDADB已优化 | 135.813 | 2.86× |

- **相对未优化EDADB：读取约87.85×加速，耗时降低98.86%。**
- **相对原始iEDA：尚未更快，耗时约为其2.86倍。**
- 主要读收益来自P1消除子表重复全表扫描；整体变化还包含移除参考DEF扫描等修改，不能全部归给P1。
- 已优化读取内部：init **0.460 ms**，read data **131.406 ms**。read data包含查询、Shadow恢复、iDB组装及清理，不含init；未优化没有对应阶段数据，不补算。

## 3. 整体写入：三者对比

| 实现 | 完整写入（ms） | 耗时倍数（该行÷原始iEDA） |
| --- | ---: | ---: |
| 原始iEDA | 6.855 | 1.00× |
| iEDA+EDADB未优化 | 2277.177 | 332.19× |
| iEDA+EDADB已优化 | 400.614 | 58.44× |

- **相对未优化EDADB：写入约5.68×加速，耗时降低82.41%。**
- **相对原始iEDA：尚未更快，耗时约为其58.44倍。**
- 写入主要受益于P3/P4减少重复提交；P5主要减少内存，不是写入加速。
- 这是完整应用操作对比：数据库完整写入包含建表、索引及提交，原生DEF不承担同样工作，差值不是“纯格式转换成本”。

已优化写入内部单独列出，全部来自P5验收的5次ON中位数：

| init（ms） | create（ms） | write data（ms） |
| ---: | ---: | ---: |
| 0.180 | 83.288 | 317.389 |

create包含建表/索引及schema提交；write data不含init/create，但包含转换、INSERT、数据事务与清理。本批没有独立COMMIT时间；各阶段中位数不保证相加等于完整命令中位数。

## 4. P1分别改善了什么？

下面使用历史P1修改前后的filler记录，热缓存5次中位数；用于说明单项作用，**不是将主表拆成逐步收益**。

| 操作 | 加P1前（ms） | 加P1后（ms） | 加速比 | 耗时变化 |
| --- | ---: | ---: | ---: | --- |
| 读取 | 19164.606 | 169.480 | 113.08× | 降低99.12% |
| 写入 | 2011.603 | 2224.625 | 0.904× | 增加10.59% |

**原因：** Point/ViaRef按父键读取从反复全表扫描变为索引查找，少检查大量无关行；没有减少查询次数。写入则增加建索引及维护索引的工作。

**结论：P1以写入和空间成本换取显著读取收益。** 这组历史读取还含参考DEF扫描，不能把169.480与主表135.813的差直接归为P3/P4/P5收益。

## 5. P3/P4分别改善了什么？

使用同一历史优化序列的filler写入记录，均为热缓存5次中位数：

| 新增修改 | 完整写入：前→后（ms） | 加速比 | 耗时降低 |
| --- | ---: | ---: | ---: |
| P3：合并建表事务 | 2224.625 → 1131.619 | 1.97× | 49.13% |
| P4：合并design数据事务 | 1131.619 → 378.269 | 2.99× | 66.57% |
| P3/P4合计，相对仅P1 | 2224.625 → 378.269 | 5.88× | 83.00% |

- **P3减少什么：** 本例15个schema事务合为1个，减少14次提交；仍执行原有CREATE TABLE/INDEX。
- **P4减少什么：** 本例10个非空root写事务合为1个，减少9次提交；INSERT记录数不变，失败整体回滚。
- **读取：** P3/P4不改读路径；该历史序列169.480→172.396 ms的变化只作回归观察，不称为读取优化收益。

另有本开发线“仅P1→再加P3/P4”的阶段记录，下面是两次实验的ON/warm中位数，不与主表总时间相减：

| 写入阶段 | 修改前（ms） | 修改后（ms） | 加速比 | 耗时降低 |
| --- | ---: | ---: | ---: | ---: |
| create | 982.339 | 89.526 | 10.97× | 90.89% |
| write data（含数据提交） | 797.298 | 259.063 | 3.08× | 67.51% |

**结论：P3主要降低建表时间，P4主要降低数据写入时间。** 两项一起启用的阶段记录支持此解释，但不是逐个事务函数的独占耗时；不能把这些节省都称作sync耗时。

## 6. P5分别改善了什么？

P5在P1/P3/P4基础上，把整组Shadow改为逐root转换、写入和释放。以下是交付前同批对照；压力输入为 **6,305,169 B**，由iRT额外复制1,000个Net路由内容构成，不是新物理有效芯片。

### 读取

| 输入 | P5前完整read（ms） | P5后完整read（ms） | 加速比 | 耗时变化 |
| --- | ---: | ---: | ---: | --- |
| filler | 141.512 | 135.813 | 1.042× | 降低4.03% |
| routed压力 | 1697.986 | 1700.133 | 0.999× | 增加0.13% |

**P5未改读路径，读取变化不当作P5加速收益。**

### 写入和内存

| 输入 | P5前完整write（ms） | P5后完整write（ms） | 加速比 | 耗时变化 |
| --- | ---: | ---: | ---: | --- |
| filler | 408.674 | 400.614 | 1.020× | 降低1.97% |
| routed压力 | 2949.917 | 3018.947 | 0.977× | 增加2.34% |

压力write data为2858.198→2876.312 ms，增加0.63%；写进程峰值RSS从302,304→273,432 KiB，**减少28.20 MiB，降低9.55%**。filler峰值仅减少52 KiB，无明显内存收益。

**结论：P5的实测价值是减少大型临时Shadow内存，而不是写入时间加速。** 两侧prepare、INSERT和事务次数相同，没有把逐root调用变成反复prepare。

## 7. 最终优化汇总：做了什么、怎样比较、结果是什么

### 最终实现

在未优化EDADB基础上，加入P1父键索引、P3统一建表事务、P4统一design写事务、P5逐root流式Shadow；另外移除已不需要的参考DEF扫描。完整设计和对象恢复保留，未包含P2按Wire批量读取。

### 最终比较方法

使用第1节同一份726,155 B的GCD filler，分别比较三种实现的**完整读、完整写命令**。总时间含各实现完成该操作需要的初始化、建表和提交；数据库内部init/create/data在第2、3节另列，不将建表并入write data。三组时间直接取各自原始记录的5次中位数，不通过累加每个P的节省推导最终时间。

### 最终结果

| 操作 | 原始iEDA（ms） | 未优化EDADB（ms） | 已优化EDADB（ms） | 已优化耗时÷原始iEDA |
| --- | ---: | ---: | ---: | ---: |
| 读取 | 47.484 | 11931.378 | 135.813 | 2.86× |
| 写入 | 6.855 | 2277.177 | 400.614 | 58.44× |

- **读：** 相对原始iEDA的耗时从251.27倍降至2.86倍；相对未优化EDADB约87.85倍加速，耗时降低98.86%。主要解决重复扫描，仍有查询与对象恢复成本。
- **写：** 相对原始iEDA的耗时从332.19倍降至58.44倍；相对未优化EDADB约5.68倍加速，耗时降低82.41%。主要减少重复提交，仍需建表、索引维护、插入及提交。
- **内存：** 独立routed压力对照中，P5减少28.20 MiB峰值RSS（9.55%）；这是另一数据集的内存收益，不加入filler时间计算。

**最终结论：已显著改善未优化EDADB，但尚未比原始iEDA DEF更快。** 上表是已有跨批次结果的汇总；各P的百分比不相加、加速比不连乘，统一逐版本复测和最终标签全矩阵复测尚未完成。本次仅更新文档，没有重新跑实验或修改原始时间。
