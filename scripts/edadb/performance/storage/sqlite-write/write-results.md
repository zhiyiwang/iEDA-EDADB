# 写入结果：批量有效，三表交错未见稳定劣势

本页保留上一轮仅写入实验及其profiling。最新文本/SQLite完整读写同批对照见[结果总览](results.md)，不要混合两批时间。

本提交保留早期写CPU采样证据，不替代最新A/B结果。提交前重新检查12份采样报告及控制统计通过，未重新采集perf；验证边界见[readme](readme.md)。

## 1. 范围与方法

仅原生SQLite C API及C++文本。本轮Release GCC 11.4、SQLite 3.37.2；版本、库路径及指纹见[manifest](results/manifest.json)、[实读配置](results/config.json)。当前执行环境不同于历史宿主机批次，只作本轮同环境比较，不把历史时间直接相减。

单表100万条8字段；三表各10万条，总30万条。每配置每组预热1次、正式5次，轮换执行顺序。正式计时不读额外计数器；全字段验证在计时外，每张表按rowid验证实际内容及顺序。计时边界见[计划](test_plan.md)。本页只分析写入，读取仅校验。

56组小规模检查、14组全量预热、70个正式样本及12次独立计数完成；[运行审计](results/audit.json)及[独立复算](results/review.json)PASS。空表、1/8/101条覆盖尾部；源码及二进制指纹未在计时运行期间改变。原始[时间](results/samples.tsv)、[计数](results/counters.tsv)、[中位数](results/summary.json)已保存，不依赖临时DB。

## 2. 单表：文本与每条SQL写1／10／100行

单位ms，5轮write data中位数。memory列中的文本仍写普通文件，不是内存文本；它是该轮的文件文本参照。

| 方式 | memory组 | disk组 |
| --- | ---: | ---: |
| 文本：格式化、输出、flush | 741.422 | 741.813 |
| SQLite：每次1行 | 1500.654 | 1585.413 |
| SQLite：每次10行 | 1009.524 | 1071.267 |
| SQLite：每次100行 | 947.786 | 1018.750 |

SQLite单行耗时约为文本的2.02／2.14倍；百行仍为1.28／1.37倍。相对单行的同轮配对净收益，十行为32.73%／32.24%，百行为36.84%／35.69%。百分比使用配对差值中位数除以单行中位数，不用独立中位数相减替代配对计算。

百行配对净差为−552.868／−565.764 ms，即每条记录约减少552.868／565.764 ns；这是整个写入路径的净差，不是一次step函数的独占耗时。

| 单表SQLite | RUN | VM_STEP | 文件库write阶段CACHE_WRITE |
| --- | ---: | ---: | ---: |
| 单行 | 1,000,000 | 16,000,000 | 10,243 |
| 十行 | 100,000 | 14,800,000 | 10,243 |
| 百行 | 10,000 | 14,080,000 | 10,243 |

绑定字段总数仍为800万，事务仍为1；REPREPARE均0。VM步数约减少12%，耗时减少约36%，不能把VM步数当作等价指令成本。写页数相同，支持减少语句执行/收尾工作，而不是少写数据的解释。缓存HIT从2,954,125降至50,829，是页缓存访问工作量变化，不是命中率降低导致退化。

**Takeaway：多行INSERT是本轮明确有效的优化；事务批量并不能替代SQL语句批量。** SQLite仍需绑定、编码记录和维护B-tree/Pager，不能期待剩余成本为零。此轮没有测STATIC组合，不叠加其历史收益。

## 3. 三表：交错还是按表写完？

均为单行INSERT，三个statement各准备一次；只改切换间隔，不减少INSERT数量。

| 顺序 | memory中位数ms | disk中位数ms |
| --- | ---: | ---: |
| t0、t1、t2逐行轮换 | 446.972 | 505.643 |
| 每表连续10行再切换 | 443.112 | 504.351 |
| t0全部→t1全部→t2全部 | 444.380 | 501.602 |

相对逐行交错，配对差值为“变体−交错”，负值更快：

| 变体 | memory中位差ms（范围） | disk中位差ms（范围） |
| --- | ---: | ---: |
| 每10行切换 | −3.912（−6.685～20.655） | +0.735（−7.392～7.485） |
| 按表完成 | −2.179（−5.967～6.256） | −3.822（−10.466～4.973） |

分组中位净收益仅0.49%／0.76%，配对范围都跨零；按30万条换算约−7.26／−12.74 ns/条，不作为稳定优化承诺。保留全部高值样本，不挑选最快一轮。

所有顺序RUN=300,000，VM_STEP=4,800,000，REPREPARE=0。内存组HIT完全相同；文件组逐行/十行写页2687，按表2684，仅差3页。

**Takeaway：本例不能证明交错INSERT是主要瓶颈；不要为不到1%且跨零的差值改写架构。** 此结论限于三个简单无额外索引表、当前缓存与数据，不能外推到很多表、长键、多索引或FK工作负载。三组共用循环、仅block不同，但净差仍包含循环及输入访问局部性，不是纯SQLite切换耗时。

## 4. 建表与提交不是write data

文件组各阶段中位数ms：

| 方式 | create | data | COMMIT |
| --- | ---: | ---: | ---: |
| 单行 | 60.853 | 1585.413 | 471.016 |
| 十行 | 62.724 | 1071.267 | 462.838 |
| 百行 | 65.415 | 1018.750 | 459.262 |
| 三表逐行交错 | 60.882 | 505.643 | 203.064 |
| 三表分组 | 63.529 | 501.602 | 205.301 |

文本flush不是fsync，不能把这些数字称为相同持久性下的完整提交对比。COMMIT是整个调用耗时，不是纯sync；data中的缓存溢出已表明提交前也可写页。当前没有I/O等待的逐项测量，不猜测fsync占比。

## 5. 独立CPU profiling

仅memory/write data，单行、百行、三表交错、三表分组各3次采样及3次无perf控制，共12+12次。使用宿主机现有sudo权限，499Hz用户态cycles、DWARF调用栈、FIFO阶段门控；没有改变perf_event_paranoid。正式时间在当前受限执行环境，profile使用独立二进制及宿主机权限，两者毫秒数不互减。采样扰动只与同profile二进制、同宿主机权限的控制比较。

[审计](results/profile-audit.json)通过，零丢样；[配对控制](results/profile-summary.json)中位差为+0.53%～+1.55%，均低于5%，仍含运行波动。三表每次仅约186～189个样本，只作粗粒度热点判断，不用小百分比差异证明某个内部函数变快。

下表为3次Children CPU采样比例的中位数，不是墙钟时间分解：

| 路线 | sqlite3_step | bind_record |
| --- | ---: | ---: |
| 单行 | 59.56% | 36.07% |
| 百行 | 38.00% | 61.66% |
| 三表交错 | 65.08% | 30.54% |
| 三表分组 | 60.37% | 36.22% |

单行VdbeHalt调用链占11.79%，它嵌套于step中，不能重复相加；百行部分报告未达到0.5%显示阈值，不将缺失值填成0。批量之后绑定成为更突出的剩余CPU路径，支持下一步绑定策略组合实验，不表示绑定绝对耗时增加。三表计数基本相同且正式配对差跨零，不能依据此CPU比例差宣称分组稳定更快。

原始perf文件及详细报告位于服务器`/tmp/sqlite-write-profile-01`，正式日志位于`/tmp/sqlite-write-run-01`。仓库保留精简采样符号、样本数及控制时间；原始perf文件不提交。
